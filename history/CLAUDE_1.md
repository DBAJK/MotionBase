## 2. 플랫폼 특성 (설계 시 준수)

- **비착용형(Non-HMD)**: 헤드셋 미착용, 바닥형/공간형 투사로 몰입 구현
- **전신 동작 인터랙션**: LiDAR 기반 위치·움직임 추적
- **보드게임 포맷**: 스포츠 테마 구역 맵에서 이동하며 칸별 퀘스트 수행
- **다인원 멀티플레이**: 1~10명
- **교육 융합**: 2023 개정 교육과정 체육 반영

### Vive와 비착용형의 관계 (해결됨)
`HTC Vive`는 헤드셋만이 아니라 **추적 시스템 전체**(HMD + 컨트롤러 + 베이스 스테이션 + 트래커)다.
플레이어는 **헤드셋을 쓰지 않고**, 베이스 스테이션이 손에 쥔 컨트롤러(배트)/신체 트래커만 추적하며 화면은 바닥·공간 투사로 본다.
SteamVR은 기본적으로 HMD를 요구하지만 **null-driver 패치**로 헤드셋 없이 구동 가능(버추얼 프로덕션·LBE 표준 방식). → 비착용형 정체성 유지.

## 3. 최종 기술 스택 결정

**Unreal Engine 단독. 백/프론트 분리 없음.**

| 필요 | 불필요 |
|---|---|
| Unreal Engine (C++ + Blueprint 혼용) | Spring / 별도 백엔드 |
| SteamVR / OpenXR (Vive 연동) | 프론트엔드 프레임워크 |
| UMG (게임 내 UI) | REST API / 웹서버 |
| SaveGame / 로컬 파일 (기록 저장) | 별도 DB 서버 |
| (선택) 생성형 AI = UE HTTP 모듈로 직접 호출 | 백/프론트 계층 분리 |

- 핵심 로직(스윙 속도·점수 공식·데이터 구조) = **C++**, 화면 연출·UI·이벤트 배선 = **Blueprint**
- **Spring/웹 대시보드는 확장 옵션**: 온라인 랭킹·원격 코칭 대시보드·AI 프록시가 필요해지면 그때 얹는다(MVP 아님).

## 4. 내부 아키텍처 (UE 안에서 계층 분리)

> "분리" = 서버 분리(❌ 실시간 지연으로 에러↑)가 아니라 **코드 모듈 분리(✅)**.

```
[Actor 계층]   ABat / APitchingZone            입력 수집·연출·충돌·UI
      │  raw 데이터(위치·속도 시계열)
      ▼
[계산 계층]   USwingAnalyzer / UPitchAnalyzer   순수 로직, UE 비의존
      │  FScoreResult 반환
      ▼
[점수 계층]   UScoringService                 3축(정확도·효율·일관성) 가중합
      │
      ▼
[결과]        UI 표시 / 로컬 저장(SaveGame)
```

**핵심 원칙**: 계산 계층은 UE(액터·렌더링)에 의존하지 않는 **순수 함수**로 작성.
입력은 숫자(FVector 배열·시간), 출력도 숫자(구조체)뿐 → **헤드셋·Vive 없이 단위 테스트 가능**.
계산 버그와 연출 버그를 분리해서 잡는다.

- 먼저 확정할 데이터 구조: `FSwingSample`, `FScoreResult` (계층 간 계약)
- 복잡 수식(궤적 피팅·회귀·편차)은 static 유틸/별도 Module로 격리

## 5. 측정 방식

### 배트 속도 (핵심)
- **컨트롤러 속도 ≠ 배트 속도**: 배트 헤드는 회전 채찍 효과로 손보다 빠름 (`v_tip = v_hand + ω×r`).
- **권장 구현**: MotionController 자식으로 `BatTip` SceneComponent(배트 길이 오프셋) 배치 → 매 프레임 월드 좌표 미분 → 회전 효과 자동 반영.
  - UE는 cm 단위 → `v_mps = v_cm / 100`
  - 링버퍼(최근 15~20샘플)로 **컨택 순간 속도**(peak 아님) / peak / 스윙 평면각 추출
  - UE 런타임 `Get Linear Velocity`(cm/s)는 손 속도만 → MVP용. 정밀은 BatTip 미분.
  - ⚠️ UE 5.7+: `Get Motion Controller Data` 폐기 → `Get Motion Controller State` 사용

### 카메라 (결론: 속도엔 불필요)
- 배트 속도 정확도는 **Vive가 카메라보다 우위**(단안 depth 모호·저fps). 카메라 추가 시 속도 정확도는 오히려 하락.
- 카메라가 유효한 영역 = **전신 폼**(하체 추진·골반 회전·X-factor). 단 **LiDAR가 골격을 주면 중복**.
- 쓰더라도 폰 + 온디바이스 포즈추정(MediaPipe/MoveNet)으로 폼 채점만. **Canon EOS 100D는 실시간 부적합**(clean HDMI 없음·30fps).
- 도입 시 MVP 아님 → 확장 단계, 가능하면 오프라인 리플레이 분석.

## 6. 점수 체계 (3축, 타격·투구 공유)

`TotalScore = w_a·정확도 + w_e·효율 + w_c·일관성`  (모드별 가중치 조정)

- **정확도**: 타이밍 오차(가우시안 감쇠), 컨택 거리(스위트스팟↔공)
- **효율**: 배트 스피드(정규화), 가상 타구 결과 / (투구=구속·하체 추진력)
- **일관성**: 지표별 표준편차(작을수록 고득점)
- **투구 확장**: 정확도=릴리스 오차, 효율=구속+하체 추진, 일관성=관절각·타이밍 편차
- ⚠️ 기준 상수(σt, d_max, v_min, v_target, σm_max)는 **실측 데이터로 캘리브레이션 필수**(하드코딩 금지)

관련 논문: 타격 = KCI #2·#3·#4 / 투구 = #6·#7·#8·#9 / 비전 검증 = #10

## 7. 개발 우선순위 (1인 · 12주)
